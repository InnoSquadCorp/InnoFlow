# Independent benchmark tooling

These standalone packages stay outside the root product dependency graph.
Read [InnoFlowBenchmarks](InnoFlowBenchmarks/README.md) and the optional
[TCA comparison](Comparison/README.md) before interpreting results.

## Advisory Apple trend (W1-0)

`trend.py` builds both independent release executables, then runs the matched
S1–S6 cohort serially on one idle Apple-silicon macOS host using **Xcode 26.6's
SDK and the official Swift 6.4.0 release toolchain**.
It never changes or invokes `compare.py`, the separate 30-pair adoption tool.
The new `Benchmark Trend (non-blocking)` workflow supports manual dispatch and
ordinary, path-filtered pull requests. It uses `macos-26`, pinned existing
checkout/upload actions, read-only repository permission, and no persisted
checkout credentials. It does not change the 28-check Release Preflight.

There are exactly **seven measured pairs per scenario**, after two paired
warmups. A is InnoFlow and B is TCA. Order alternates AB/BA within each scenario;
the starting side alternates by scenario, yielding 21 AB and 21 BA measured
pairs across the full cohort. Each side of each pair is a fresh process.
Counts and scenarios are fixed, not command-line tuning options:

| Scenario | Iterations per process | Workload |
| --- | ---: | --- |
| S1 | 100,000 | One synchronous action |
| S2 | 20,000 | One root plus ten synchronous descendant actions |
| S3 | 2,000 | 1,000 retained row projections, one row update per iteration |
| S4 | 30,000 | 100 retained derived read models, unrelated root update |
| S5 | 100,000 | Actual SwiftUI binding update |
| S6 | 2,000 | TestStore send/receive round trip |

The executables exclude setup from their timed regions and check final state.
The runner independently validates each scenario's expected checksum,
iteration count, positive finite duration, and measured status. It rejects
malformed/duplicate JSON fields, missing S5, failed or timed-out processes,
duplicate samples, order changes, and any incomplete cohort, including missing
warmups. Such captures exit nonzero and publish **no summary timing metrics**;
partial raw evidence remains available. The workflow tolerates that failure
because it is advisory, not because the capture is valid.

### Evidence and reproducibility

Artifacts contain:

- exact repository SHA, dirty-source status/diff, copied benchmark/library
  sources with SHA-256 hashes, and executable hashes
- Swift and Xcode versions, host/architecture details, runner image metadata,
  and the effective package tools-version requirements
- selected macOS platform/runtime search paths, Testing.framework binary hash,
  executable linkage/load commands, and paired warmup dyld loading traces
- both packages' original `Package.resolved` files at available before/build/
  after/final stages, file hashes, and resolved dependency versions/revisions
- raw stdout/stderr and command/exit/timeout receipts, including build failures
  and partial timeout output; validated warmup/measurement samples in JSONL
- `manifest.json`, machine-readable `summary.json`, and readable `summary.md`

Both builds finish before measurement. Existing pins may not change during a
build, and source/binary/resolved-file changes during capture invalidate it.
TCA must resolve exactly to **1.26.2**. Both standalone `Package.resolved`
files are explicitly unignored commit candidates generated by real SwiftPM
resolution on **Linux with the official Swift 6.4.0 distribution, 2026-10-03**.
InnoFlow resolves one pin, SwiftSyntax 604.0.0, matching the root lock. The TCA
package resolves 15 pins, including TCA 1.26.2, SwiftSyntax 604.0.0, and
OpenCombine 0.14.0. No product was built to obtain these locks.

These pins were initially **Linux-resolved candidates**. The
upstream [combine-schedulers 1.2.2 manifest](https://github.com/pointfreeco/combine-schedulers/blob/114354e8c1667a2edc4993700fb9fa4f90157b56/Package.swift)
enables the `OpenCombineSchedulers` default trait when Darwin cannot be
imported, and its OpenCombineShim dependency is Linux/Android-specific.
Other host/compiler-conditioned manifests may also affect resolution. The
Apple capture must verify the committed graph and may produce different
pins or lock metadata. Any existing lock change remains incomplete, with
before/final files preserved for review; do not silently accept it or publish
timings from that capture. Review and commit any required Apple lock refresh
before rerunning. A Linux resolve or a committed lock is not Apple build proof.

The comparison package and TCA 1.26.2 require Swift tools 6.4, while
Xcode 26.6 bundles Swift 6.3. The workflow therefore installs the fixed official
[Swift 6.4.0 macOS package](https://download.swift.org/swift-6.4.0-release/xcode/swift-6.4.0-RELEASE/swift-6.4.0-RELEASE-osx.pkg)
in the hosted runner's user toolchain directory. It checks the package's
signature against `Developer ID Installer: Swift Open Source (V9AUD2URP3)`
and requires successful Gatekeeper assessment before installation. Rejected
signatures or assessments stop the job; no security setting is changed.

The [official Swift macOS installer instructions](https://www.swift.org/install/macos/package_installer/)
describe installing a release `.pkg` and selecting its toolchain with
`TOOLCHAINS` or `xcrun --toolchain`. Selection reads the actual installed
`CFBundleIdentifier`, requires exactly one official 6.4.0 release match, and
checks that both command-line Swift and `xcrun` select it. The artifact records
download SHA-256, signature/Gatekeeper/install logs, selected Info.plist and
identifier, Swift version, compiler paths, and macOS SDK details. The official
macOS download page did not provide an independently verified package checksum
at implementation time: the recorded hash is **observed evidence**, not a
prevalidated checksum pin. Keep this limitation in first-run review.
The release guard accepts both `6.4 / swift-6.4-RELEASE` (observed in the
official Linux distribution) and `6.4.0 / swift-6.4.0-RELEASE` version
spellings. It rejects later patches, development snapshots, and other builds;
the macOS download URL remains pinned to 6.4.0.

That CI build evidence applies to its recorded SHA only. Each new capture must
repeat Apple compilation and validation of the transitive pins. A missing or wrong
toolchain remains incomplete; no newer-toolchain fallback or manifest rewrite
is allowed. Do not lower either package's tools version.

Directly launching these executables also needs the selected Xcode's testing
runtime search paths. Following SwiftPM's
[SDK platform path derivation](https://github.com/swiftlang/swift-package-manager/blob/main/Sources/PackageModel/SwiftSDKs/SwiftSDK.swift)
and [test runtime environment setup](https://github.com/swiftlang/swift-package-manager/blob/main/Sources/Commands/Utilities/TestingSupport.swift),
the runner uses `xcrun --sdk macosx --show-sdk-platform-path` and verifies that
the platform and SDK belong to the selected Xcode. It checks the actual
`Developer/Library/Frameworks/Testing.framework/Versions/A/Testing` binary,
records its SHA-256 and linkage, and supplies the same platform framework,
private-framework, and library directories to both benchmark processes through
`DYLD_FRAMEWORK_PATH` and `DYLD_LIBRARY_PATH`. Existing nonempty `DYLD_*`
settings are rejected instead of admitting unverified runtime overrides.

The first paired warmup of each scenario enables `DYLD_PRINT_LIBRARIES` for
both sides and verifies any loaded Testing.framework against that exact binary;
linked Testing.framework requires a matching load. The second paired warmup and
all measured processes omit loader tracing. The 108-process schedule, workload
counts, Release build arguments, and product sources are unchanged. Missing
frameworks, absent/mismatched loading evidence, or a changed framework hash
leave the capture incomplete with no summary metrics. There is no alternate
Xcode/toolchain/framework fallback.

`publication_ready` only describes clean source and committed, unchanged pins
after a complete capture. It grants no permission to publish and is not a
statistical, correctness-suite, release, or framework-quality verdict.

### Commands

Pure Python validation does not run Swift or download dependencies:

```sh
python3 -B Benchmarks/trend.py --self-test
```

After the exact toolchain/SDK combination above is prepared and validated, an
approved quiet Apple host can run the capture. Select the installed Swift 6.4.0
toolchain as documented above. Use a new output path outside the checkout; do not
run concurrent builds, tests, or unrelated CPU-heavy jobs:

```sh
DEVELOPER_DIR=/Applications/Xcode_26.6.app/Contents/Developer \
  python3 -B Benchmarks/trend.py --output /tmp/innoflow-trend-unique-run
```

The capture directory also contains temporary build products under `build/`.
CI excludes that subtree from the evidence upload. Preserve the remaining
files together; results without raw evidence are not a complete report.

### Interpretation

Reports show median/min/max ns per scenario iteration and seven paired
TCA/InnoFlow ratios, with no pass/fail speed threshold or overall score.
An S2 iteration contains eleven reductions, so its unit is not one action.
S4 uses Combine-backed TCA `ViewStore` versus InnoFlow `SelectedStore`;
they are retained read-model counterparts with different implementations.
Seven paired processes on a shared CI runner provide a small trend signal,
not universal framework rankings or stable population estimates. Compare
captures only after checking source, pins, hardware, toolchain, workload, and
order metadata; runner noise can dominate changes. No automatic cross-run
baseline, adoption decision, or Apple absolute target is asserted here.

## Paired local adoption and final non-regression

`compare.py` is a separate fixed 30-pair, two-warmup comparator. It requires an
actual-invocation build-admission receipt identifying both immutable executables
and every supported workload (Linux omits only Apple-only S5). With
`--purpose improvement` (default), S1/S2 paired medians and bootstrap95% upper
bounds must be <=0.95 and all supported median ratios <=1.05. With
`--purpose non-regression`, every supported paired median and bootstrap95% upper
bound must be <=1.05. This second purpose connects a subsequently corrected
source snapshot to an already measured optimization; it does not demand another
5% speedup. Freeze the purpose before collecting data and never pool cohorts.

A complete capture can exit0 with `decision: not-established`: read the summary
gate, not merely the process exit status. Failure, timeout, missing checksum or
changed executable/admission makes a capture incomplete. Record independent
quiet-window coordination and input hashes externally. The runner itself is not
a machine-wide process isolation mechanism. Confidence intervals describe
paired process loop wall-time ratios, not CPU time or individual action latency.
